# 하나의 매물 데이터를 세 플랫폼에 나눠 넣기 — 설계 노트

플랫폼별 폼 구조는 [`captures/`](../captures/2026-09-08-현장수집/) 의 `DOM-전수조사.md` 세 편에 있다.
이 문서는 그 셋을 **가로로 잘라** 본 것이다. 값 하나가 세 곳에 각각 어떤 이름·단위·형식으로 들어가는지,
그래서 어댑터를 어떻게 나눠야 하는지를 다룬다.

> 이 문서의 모든 표는 2026-09-08 현장 수집 기록(필드로그 JSON 3개)에서 **직접 다시 확인한 것**이다.
> 확인하지 못한 것은 **미확인**으로 표시했다. 추정으로 채우지 않았다.
> 근거를 되짚으려면 각 플랫폼 문서의 조작 id(`[a17]`)와 초 단위 시각을 따라가면 된다.

---

## 1. 결론부터 — 왜 어댑터를 플랫폼마다 따로 짜야 하나

세 플랫폼은 **화면이 비슷할 뿐 안은 완전히 다르다.** 공통 코드로 덮을 수 있는 부분이 거의 없다.

| | 당근 | 직방 | 다방 |
|---|---|---|---|
| UI 기반 | React + 자체 디자인시스템 | Radix(shadcn) + react-hook-form | styled-components |
| `<form>` 요소 | **없음** | 있음 | 이름칸 1개만 감쌈 |
| `<select>` 개수 | **0** | 15 (**숨은 미러**) | **12 (진짜)** |
| 무엇으로 칸을 찾나 | `name` | 의미 있는 `id` | **표의 행 제목 텍스트** |
| 켜짐/꺼짐 읽기 | `input.checked` | `aria-checked`/`data-state` · **일부는 클래스뿐** | `input.checked` |
| 드롭다운 조작 | 인라인 버튼 목록 | 포털 listbox | **네이티브 select** |

*(개수는 각 캡처의 마지막 상태 DOM 기준. 직방 s4 · 다방 s2 · 당근 s2)*

**같은 함수로 세 곳을 채우려 하면 반드시 실패한다.** 정규화된 payload 하나를 두고,
플랫폼마다 번역기를 따로 두는 구조가 필요하다.

```
매물 데이터 1벌
   ├─ 당근 어댑터 → name 으로 찾고, 라벨 클릭, 인라인 목록에서 텍스트로 선택
   ├─ 직방 어댑터 → id 로 찾고, 포털 목록에서 텍스트로 선택, 상태는 클래스로 확인
   └─ 다방 어댑터 → 표 행 제목으로 찾고, 네이티브 select 에 값 대입
```

## 2. 같은 값인데 다르게 들어가는 것 ★

가장 많이 깨지는 지점이다. 아래는 전부 캡처의 DOM에서 직접 읽은 것이다.

### 2-1. 금액 단위 — 직방은 **한 폼 안에서** 만원과 원이 섞인다

| 값 | 당근 | 직방 | 다방 |
|---|---|---|---|
| 보증금 | `trades.N.price` → 「만원」 | `sales.deposit` → 「만원」 | `deposit` → 「만원」 |
| 월세 | `trades.N.monthlyPay` → 「만원」 | `sales.rent` → 「만원」 | `price` → 「만원」 |
| 관리비 | `totalManageCost` → 「만원」 | `manageCostDetail.detail.normalManageCost.amount` → **「원」** ⚠ | (조건부 · 미확인) |

단위는 입력칸 **바로 뒤 `<span>`** 에 적혀 있다. 직방 보증금은
`<input name="sales.deposit"><span class="ml-1">만원</span>`,
관리비 정액 금액은 같은 자리에 `<span class="ml-1">원</span>` 이다.

**관리비 30만원**을 넣는다면 — 당근 `30`, 직방 `300000`.
같은 어댑터 안에서도 칸마다 단위를 확인해야 한다. **칸 옆 `<span>` 텍스트를 읽어 검산할 것.**

### 2-2. 면적 — 단위와 칸 수가 다르다

| | 입력 칸 | 평 표시 |
|---|---|---|
| 당근 | `input[name=area][type=number]` (단위 `m²`) + 평 칸 **하나 더** | **㎡↔평 양방향 자동환산.** 한쪽만 채울 것 |
| 직방 | `input[name=sizeM2]` 하나 (단위 `㎡`) | 라벨에 `16.64평` 이 **계산돼 표시만** 된다. 입력칸이 아니다 |
| 다방 | `input[name=room]` 이 **2개** — placeholder `평수 입력` / `㎡ 입력` | **미확인.** 이 칸에 값을 넣어 보지 않았다 |

⚠ **당근은 양쪽(㎡·평)을 다 채우면 서로 덮어써서 값이 깨진다.**

⚠ **다방은 이름이 겹친다.** `input[name=room]` · `input[name=supply]` 가 각각 2개씩이고
평/㎡ 구분은 **placeholder 로만** 된다. `querySelector` 로 첫 번째를 잡으면 평 칸이 걸린다.

### 2-3. 방향 — 코드도 순서도 셋 다 다르다

| 뜻 | 당근 (버튼 텍스트) | 직방 `roomDirection` | 다방 (이름 없는 select) |
|---|---|---|---|
| 동 | `동향` | `E` | `EAST` |
| 서 | `서향` | `W` | `WEST` |
| 남 | `남향` | `S` | `SOUTH` |
| 북 | `북향` | `N` | `NORTH` |
| 북동 | `북동향` | `NE` | `NORTH_EAST` |
| 남동 | `남동향` | `SE` | `SOUTH_EAST` |
| 북서 | `북서향` | `NW` | `NORTH_WEST` |
| 남서 | `남서향` | `SW` | `SOUTH_WEST` |

**화면에 놓인 순서는 셋이 전부 다르다.**

```
당근   남 · 동 · 서 · 북 · 남동 · 남서 · 북서 · 북동
직방   동 · 서 · 남 · 북 · 북동 · 남동 · 북서 · 남서
다방   동 · 서 · 남 · 북 · 북동 · 북서 · 남동 · 남서
```

**순서를 믿고 인덱스로 고르면 남동과 북서가 뒤바뀐다.** 값(직방·다방)이나 텍스트(당근)로 고를 것.

### 2-4. 층 — 지하·옥탑 표현이 제각각

| | 전체 층 | 해당 층 |
|---|---|---|
| 당근 | `topFloor` `<input type=number min=1 step=1>` | `floor` `<input type=number step=1>` + 지하·반지하 체크박스 별도 |
| 직방 | `floorAll` select `1`~`80` | `floor` select — `반지하` / `1`~`N` / `옥탑방` **(값에 한글이 섞임)** |
| 다방 | select `""`+`1`~`50` (오피스텔·아파트는 `55`까지) | select — `-1`=반지층, `0`=옥탑, `1`~ |

⚠ **다방 「해당 층」은 값이 중복된다.** 주소 검색 뒤 목록이 14개로 재생성되는데,
그때 `value="0"` 이 **「옥탑」과 「0층」 둘 다에** 붙는다. 값으로 고르면 어느 쪽이 선택될지
보장되지 않는다. **텍스트로 골라야 한다.**

⚠ **직방 「해당 층」 목록은 「전체 층」을 먼저 골라야 만들어진다.**

### 2-5. 날짜 — 형식이 셋 다 다르고, 직방 입주일은 타이핑이 막혀 있다

| | 사용승인일 | 입주 가능일 |
|---|---|---|
| 당근 | `buildingApprovalDate` — placeholder `YYYY-MM-DD`, 예 `2012-10-07` | `moveInDate` — **같은 형식** |
| 직방 | `approveDate` — `maxlength=20`, 예 `20260808` (**구분자 없음**) | `moveInDate` — **`readonly` ⚠** |
| 다방 | `2026.07.15` (**점**) · 이름 없음 | 같은 형식 · 이름 없음 |

**직방 입주 가능일은 `readonly=""` 라 값을 써넣을 수 없다.** 캘린더를 열어
연·월을 맞추고 → `button[name="day"]` 를 누르고 → **하단 확정 버튼까지** 눌러야 한다.

당근은 인페이지 달력이 없다(브라우저 네이티브 picker). 대신 **텍스트 칸에 직접 타이핑이 된다.**
단, 타이핑 도중 하이픈이 자동으로 붙는다: `1999` → `1999-08` → `1999-08-15`.

### 2-6. 거래 유형 — 데이터 모델 자체가 다르다 ★★

| | 방식 | 선택지 |
|---|---|---|
| 당근 | **체크박스 — 복수 선택 가능** | 월세 · 매매 · 전세 · 연세 · 단기 |
| 직방 | 토글 버튼 — 택1 | **전세 · 월세** (매매 없음) + 별도 체크박스 `#isShortTerm` 「단기 매물」 |
| 다방 | 라디오 — 택1 | 매매 · 전세 · 월세 + 별도 체크박스 「단기임대」 |

**이게 payload 설계를 좌우한다.**

- **당근은 한 매물에 여러 거래유형을 동시에** 걸 수 있다. 체크할 때마다 `trades.N.*` 묶음이 생긴다
- **직방 원룸 폼에는 「매매」가 없다.** 매매 매물은 이 폼으로 올릴 수 없다
- 「단기」는 당근에선 거래유형 중 하나, 직방·다방에선 **별도 체크박스**다

⇒ payload 는 `거래유형: [목록]` 으로 두고, 직방·다방 어댑터가 **하나만 골라 넣는 규칙**을 갖는 편이 안전하다.

**당근의 `trades.N` 은 고정 번호가 아니다.** 관측된 것:

| 체크한 상태 | 생긴 이름 |
|---|---|
| 매매만 / 전세만 / 연세만 / 단기만 | 각각 `trades.0.*` |
| 5개 모두(월세→매매→전세→연세→단기 순) | `.0`=월세 `.1`=매매 `.2`=전세 `.3`=연세 `.4`=단기 |

이 캡처에서는 **화면 순서와 클릭 순서가 항상 같아서** N 이 어느 쪽을 따르는지 구분할 수 없었다.
**N 을 계산해 셀렉터에 박지 말 것.** 가격 블록의 **제목(월세/매매/전세/연세/단기)** 으로 블록을 찾고
그 안의 `input[name^="trades."][name$=".price"]` 를 잡는다.

유형마다 딸린 칸도 다르다 — 매매·전세는 `price` 하나, 월세·연세는 `price`+`monthlyPay`+`adjustable`,
단기는 `price`+`monthlyPay`+`description`(maxlength 100).

### 2-7. 방 수 — 직방에는 그 칸이 없다

| | 방 수 | 욕실 수 |
|---|---|---|
| 당근 | `roomCnt` `<input type=number>` | `bathroomCnt` `<input type=number>` |
| 직방 | **없음.** `roomType` select 로 대체 — `01`=오픈형 원룸 (방1) · `02`=분리형 원룸 (방1,거실1) · `03`=복층형 원룸 | `bathroomCnt` **select** `1`~`5` |
| 다방 | 이름 없는 `<input type=text inputmode=numeric>` | 같음 |

⇒ 「방 2개」를 직방에는 **그대로 넣을 수 없다.** 구조 선택지로 바꾸는 규칙이 필요하고,
그 규칙은 이 조사만으로 정할 수 없다(선택지가 3개뿐이라 방 2개 이상을 표현할 수단이 없다). **미해결**

## 3. 값을 넣는 방법도 다르다

### 3-1. 텍스트·숫자 칸 — 세 곳 모두 React 제어 컴포넌트다

`el.value = "10"` 만으로는 **화면만 바뀌고 내부 상태는 안 바뀐다.** 저장하면 빈 값이 된다.
네이티브 setter 를 거쳐 `input` 이벤트를 올려야 한다.

```js
const setter = Object.getOwnPropertyDescriptor(HTMLInputElement.prototype, "value").set;
setter.call(el, "10");
el.dispatchEvent(new Event("input", { bubbles: true }));
```

- **기존 값이 있으면 먼저 비우고 넣는다.** 당근 숫자 칸에서 자릿수 누적이 관측됐다(`1`→`11`, `31`→`311`)
- **다방 `inputmode="numeric"` 칸은 문자 입력을 거절한다.** 숫자만 넣을 것

### 3-2. 체크박스·라디오 — `checked` 직접 대입 금지

| | 실제 요소 | 눌러야 할 것 | 상태 확인 |
|---|---|---|---|
| 당근 | `<input>` 이 `clip:rect(0,0,0,0)` 으로 **숨겨짐**, `<label>` 안 | `<label>` 또는 `input.click()` | `input.checked` (**눈에 보이는 표시는 별도 `<div>`**) |
| 직방 | `<button role="checkbox">` + 숨은 미러 input | **button** | `aria-checked` · `data-state` |
| 다방 | 네이티브 `<input>` | 그냥 클릭 | `input.checked` |

`el.checked = true` 는 React `onChange` 를 발생시키지 않는다. **클릭 경로로 가야 한다.**
그리고 **누르기 전에 현재 상태를 반드시 읽어야 한다** — 켜져 있는 걸 또 누르면 꺼진다.

⚠ **직방 토글 버튼(거래 유형 등)은 예외다.** `aria-*` 도 `data-state` 도 없다.
선택 여부가 **클래스에만** 있다.

```
선택됨    border-orange-500 text-orange-500
선택안됨  border-input      text-secondary-foreground
```

⚠ **다방 버튼 그룹도 `aria-pressed`·`data-state`·`disabled` 가 전혀 없다.**
선택된 버튼만 생성 클래스가 다른데, 그 클래스는 빌드마다 바뀌는 해시다. **텍스트로 찾을 것.**

### 3-3. 드롭다운 — 셋이 완전히 다르다

| | 구조 | 조작 |
|---|---|---|
| 다방 | **진짜 `<select>` 12개** | 값 대입 + `change` 이벤트. **가장 쉽다** |
| 직방 | `button[role=combobox]` + **숨은 `<select>` 미러 15개** | 미러에 값을 써도 **안 먹는다**(Radix→select 단방향). 트리거 클릭 → 포털 `[role=option]` 을 텍스트로 클릭 |
| 당근 | `button[name=…]` — `<select>` 0개, 목록은 **열기 전엔 DOM 에 없다** | 트리거 클릭 → 그 자리에 생기는 `<button>` 을 텍스트로 클릭 |

직방의 숨은 `<select>` 는 **옵션 카탈로그를 읽는 용도로는 완벽하다.** `value ↔ 텍스트` 대응을
거기서 먼저 읽어 두고, 그 텍스트로 포털 목록 항목을 찾는 방식이 안전하다.

당근은 매물 종류 11 · 건축물 용도 29 · 방향 8이 **목록을 열어야 생성된다.** 미리 읽을 수 없다.

### 3-4. 셀렉터 — 무엇을 붙잡고 무엇을 피하나

| | 1순위 | **절대 쓰면 안 되는 것** |
|---|---|---|
| 당근 | `input[name="area"]` 등 의미 있는 `name` | **`id` 전부** — `field:_r_54_:input` 꼴. 새로고침마다 100% 바뀜(2회 로드 대조). `name` 이 `_r_5q_` 꼴이면 그것도 사실상 id 다 |
| 직방 | 고정 `id` — `haveNoDong` `isShortTerm` `moveInImmediately` `no-parking` `no-manage-cost` 등 (체크박스·라디오 19개) | `:r39:-form-item` 꼴 — 콜론 이스케이프가 필요하고 렌더 순서에 의존한다 |
| 다방 | **`<tr>` 의 `<th> <h1>` 텍스트** | `name`·`id`·`data-*` 가 거의 없다. 고유 `name` 10개뿐이고 그중 절반이 중복이다. 클래스는 빌드 해시 |

**이름이 겹치거나 도중에 바뀌는 것들:**

- 당근 `requiredOptions` — 대출·반려동물·주차 8개가 **모두 같은 이름**. 행 제목으로 먼저 좁힐 것
- 다방 `room`·`supply` — 각각 2개(평/㎡)
- 다방 `dong` — 동 입력 input 과 단지명 검색 select 가 **같은 이름**
- 다방 — 「건물 유형 = 건물 전체」를 고르면 **같은 요소의 `name` 이 바뀐다**:
  `room`→`totalFloor`, `supply`→`land`. **`name` 을 캐싱하지 말 것**

⚠ **직방 주소 칸의 `name` 은 `lat` 이다.** 위도가 아니라 **주소 문자열**이 들어간다
(`data-sentry-source-file="AddressField.tsx"`, `readonly`). 이름만 보고 판단하면 안 된다.

## 4. 순서를 지켜야 하는 곳

세 플랫폼 모두 **먼저 정해야 다음 칸이 생기는** 구조가 있다. 순서를 어기면 칸이 없거나 값이 날아간다.

```
당근  ① 주소 → ② 매물 종류 → ③ 건축물 용도 → ④ 거래 유형 → ⑤ 가격 → ⑥ 나머지
      ⚠ 거래 유형을 나중에 바꾸면 가격 블록이 통째로 리마운트되며 입력값이 사라지고
        id 도 새로 발급된다 (`field:_r_7f_` → `field:_r_85_`).
        입력과 검증은 반드시 같은 사이클 안에서 끝낼 것

직방  ① 주소(팝업) → ② 건물 종류 → ③ 거래 유형 → ④ 보증금·월세
      → ⑤ 전체 층 → ⑥ 해당 층 → ⑦ 관리비(부과 방식 먼저) → ⑧ 사진
      ⚠ 「해당 층」 목록은 「전체 층」에 따라 만들어진다
      ⚠ 「전세」를 누르면 `sales.rent` 가 사라지고 「단기 매물」 체크가 **저절로 풀린다**

다방  ① 대분류 → ② 소분류(건물 유형) → ③ 주소 → ④ 면적 → ⑤ 거래 종류 → ⑥ 가격 → ⑦ 층 → ⑧ 나머지
      ⚠ 「건물 전체」를 고르면 같은 요소의 name 이 room→totalFloor, supply→land 로 바뀐다
      ⚠ 단지명 3단 드롭다운(시/도→시군구→동)은 상위를 고르기 전엔 하위가 disabled
      ⚠ 「미등기건물」을 체크하면 **「매매」 라디오가 disabled 로 막히고**
        매매 전용 칸(`takeTenantDeposit`·`takeTenantPrice`)이 제거된다
```

**공통 원칙: "값을 넣었다" 가 아니라 "다음 칸이 나타났다" 를 기다려야 한다.**
당근 실측으로 조작 → 칸 생성까지 **최소 0.24초 · 중앙값 0.47초 · 최대 4.65초**였다.
고정 대기 0.5초로는 부족하다. `MutationObserver` 나 조건 폴링을 쓸 것.

## 5. 넣고 나서 확인하기

값이 그대로 남는다고 가정하면 안 된다. 실제로 관측된 것들:

| 현상 | 어디서 |
|---|---|
| 천단위 콤마 자동 삽입 (`6545` → `6,545`) | 직방 `sales.rent` |
| ㎡↔평 양방향 자동환산 — **양쪽 다 채우면 서로 덮어쓴다** | 당근 면적 |
| 날짜 하이픈 자동 삽입 (`1999` → `1999-08`), 자릿수 초과분 무시 | 당근 `moveInDate` |
| 숫자 칸 자릿수 누적 (`1`→`11`) | 당근 (기존 값을 비우지 않으면) |
| 문자 입력 거절 | 다방 `inputmode="numeric"` 칸 |
| 조건 변경으로 칸 자체가 제거됨 | 직방 「전세」→`sales.rent` · 다방 「미등기건물」→매매 전용 칸 |

⇒ **넣은 뒤 다시 읽어 확인하는 단계를 어댑터에 넣어야 한다.**
특히 금액·면적·날짜는 넣은 값과 남은 값이 다를 수 있다. 검증은 **문자열 비교가 아니라
정규화 후 비교**여야 한다(콤마·하이픈·자동환산 때문에).

## 6. DOM 조작으로는 안 되는 곳

| | 무엇 | 왜 |
|---|---|---|
| 직방 | **주소 검색** | 별도 브라우저 창(`windowName: "zikim-search-address"`) 안의 카카오 우편번호 **교차출처 iframe** |
| 다방 | **주소 검색** | 같은 구조 — 팝업 창 + 카카오 교차출처 iframe |
| 직방 | `input[name=lat]`(주소) | `readonly`. 팝업 콜백이 폼 상태를 직접 갱신하며, **입력 이벤트가 0건**이었다. 써넣어도 폼 상태가 안 바뀔 가능성이 높다 (**미검증**) |
| 당근 | 주소 모달 | 같은 문서 안이라 조작은 가능하나, 「빠른 단지 선택」칩이 **그 계정이 최근 다룬 주소 이력**이다. 건드릴 대상이 아니다 |
| 공통 | 사진 업로드 | 파일 선택 대화상자 |

**주소는 별도 설계가 필요하다.** 확장의 다른 컨텍스트에서 처리하거나,
사람이 한 번 개입하는 방식이 현실적이다.

## 7. 아직 정하지 못한 것

이 조사만으로는 답이 안 나온 것들이다. 구현 전에 결정하거나 재수집이 필요하다.

| 항목 | 상태 |
|---|---|
| **매물 내리기(삭제·광고종료)** | **자료 없음.** 등록폼만 조사했다. 매물 관리 화면은 한 번도 캡처하지 않았다 |
| 당근 `trades.N` 의 N 규칙 | 화면 순서인지 클릭 순서인지 **구분 불가** (§2-6). 블록 제목으로 찾을 것 |
| 다방 ㎡↔평 자동환산 여부 | **미확인.** 면적 칸에 값을 넣어 보지 않았다 |
| 다방 관리비 칸의 단위 | **미확인.** 조건부로만 나타나는데 그 조건을 밟지 않았다 |
| 방 수 → 직방 구조 선택지 매핑 | 직방 선택지가 3개뿐이라 방 2개 이상을 표현할 수단이 없다 |
| 직방 `sales.deposit` 의 콤마 여부 | 관측 값이 `56` 이라 미확인. `rent` 와 같은 컴포넌트라 같을 가능성이 높으나 **미검증** |
| 당근 매물 종류 11종 중 7종의 조건부 칸 | 4종만 눌러 봤다 |
| 유효성 검사·에러 메시지 | 등록 버튼을 누르지 않아 전무 |

## 8. 구현 순서 제안

1. **정규화 payload 스키마를 먼저 정한다.** §2 의 차이를 흡수할 수 있는 형태여야 한다
   — 거래유형은 목록, 금액은 단위를 명시, 방향·층은 자체 코드
2. **플랫폼별 번역표를 데이터로 둔다.** §2-3 방향 코드처럼 값 대응은 코드가 아니라 표로.
   폼이 바뀌면 표만 고치면 되게
3. **조작 계층을 플랫폼별로 분리한다.** §3 대로 셋이 다르다. 공통화할 수 있는 건
   "네이티브 setter + input 이벤트" 정도뿐이다
4. **한 칸 넣을 때마다 읽어서 검산한다.** §5. 정규화 후 비교할 것
5. **순서와 대기를 명시적으로 모델링한다.** §4. 고정 `sleep` 금지
6. **실제 사이트에서 등록 버튼을 누르지 않는 드라이런**으로 검증한다.
   폼 구조는 언제든 바뀐다. **이 문서의 조사 시점은 2026-09-08 이다.**
