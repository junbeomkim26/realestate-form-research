# 재현/ — 캡처한 등록폼을 되살린 것

`captures/` 의 SingleFile 스냅샷은 **완전히 죽어 있다.** SingleFile 이 저장할 때
`<script>` 를 전부 걷어내기 때문에(직방 스냅샷의 script 태그 수 = **0**), 화면은 그대로지만
드롭다운을 눌러도 열리지 않고 체크박스도 반응하지 않는다.

여기서는 그 껍데기 위에 **`DOM-전수조사.md` 로 확인한 동작만** 다시 얹는다.
원본 스냅샷은 읽기만 하고 건드리지 않는다.

```
재현/
├── README.md      ← 이 문서
├── serve.py       정적 서버 (평소엔 필요 없다 — 아래 참조)
├── 직방/
│   ├── build.py   원본 스냅샷 → 재현본 생성
│   ├── live.js    주입되는 상호작용 스크립트
│   └── 직방_매물등록폼_재현.html   (생성물 · git 미추적)
├── 다방/
│   ├── build.py
│   ├── live.js
│   └── 다방_매물등록폼_재현.html   (생성물 · git 미추적)
└── 당근/
    ├── build.py
    ├── live.js
    └── 당근_매물등록폼_재현.html   (생성물 · git 미추적)
```

## 만들고 여는 법

```bash
python3 재현/직방/build.py     # 직방
python3 재현/다방/build.py     # 다방
python3 재현/당근/build.py     # 당근
```

그리고 **만들어진 파일을 그냥 더블클릭하면 된다. 서버가 필요 없다.**

```
재현/직방/직방_매물등록폼_재현.html   ← Finder 에서 더블클릭 (또는 브라우저에 끌어다 놓기)
재현/다방/다방_매물등록폼_재현.html
재현/당근/당근_매물등록폼_재현.html
```

재현본은 **혼자서 다 돌아간다.** 확인한 내용:

| 항목 | 개수 |
|---|---:|
| `<iframe>` | 0 |
| 외부 script · stylesheet · 이미지 | 0 |
| CSS 안의 외부 `url()` | 0 |
| `fetch` / `XMLHttpRequest` | 0 |
| `localStorage` / service worker | 0 |
| 내장된 자원 (`data:` URI) | 9 |

SingleFile 이 이미지·글꼴·CSS 를 전부 파일 안에 넣어 두었고, `live.js` 도 인라인으로 심는다.
그래서 인터넷도, 서버도, 다른 파일도 필요 없다. **이 파일 하나만 있으면 된다** — 팀원에게 그대로 보내도 열린다.

<details>
<summary>serve.py 는 왜 있나 (평소엔 안 써도 된다)</summary>

`file://` 로 열면 브라우저가 막는 기능이 몇 가지 있다 — 교차출처 iframe 접근, 일부 자동화 도구의 접근 등.
직방 재현본은 그런 걸 하나도 안 써서 상관없지만, 앞으로 만들 재현본이 iframe 을 쓰게 되면 필요해진다.
그때는 이렇게 쓴다.

```bash
python3 재현/serve.py 8779     # http://localhost:8779/직방/직방_매물등록폼_재현.html
```

`OSError: [Errno 48] Address already in use` 가 나오면 그 포트를 이미 누가 쓰고 있는 것이다.
다른 번호를 주거나(`python3 재현/serve.py 8780`), 쓰고 있는 것을 찾아 끈다.

```bash
lsof -ti :8779 | xargs kill      # 8779 를 물고 있는 것을 끈다
```
</details>

생성물(7MB)은 git 이 추적하지 않는다. 원본 스냅샷도 추적되지 않으므로,
**`captures/2026-09-08-현장수집/직방/singlefile/` 에 원본이 있어야 빌드된다.**

## 감사 — 원본에 없는 것이 섞이지 않았나

재현본은 "눌러볼 수 있는 그림"이지만, **DOM 조작 자동화의 참고자료로 쓰일 수 있으므로
원본에 없는 식별자가 등장하면 안 된다.** 실제로 대조했다.

### 정적 대조 — 원본 스냅샷 vs 재현본 HTML

`<script>` 를 제외하고 태그·`name`·`id`·`role`·`data-*` 를 전수 비교했다.

| | name | id | role | data-* | 태그 수 |
|---|---|---|---|---|---|
| 직방 | 40 = 40 | 52 = 52 | 7 = 7 | 9 = 9 | 차이 없음 |
| 다방 | 24 = 24 | 22 = 22 | 1 = 1 | 2 = 2 | 차이 없음 |
| 당근 | 51 = 51 | 30 = 30 | 4 = 4 | 21 = 21 | 차이 없음 |

**추가도 삭제도 0건.** 재현본의 정적 HTML 은 원본과 구조가 같고, 주입한 `<script>` 하나만 다르다.

### 런타임 대조 — 기능을 전부 눌러 본 뒤

드롭다운·토글·체크박스·조건부 칸·달력·관리비 갈래를 모두 발동시킨 뒤 DOM 전체를 훑어,
**필드로그(상태 DOM·조작 문맥·오버레이) + SingleFile 스냅샷** 에 실재했던 식별자 집합과 대조했다.

| | 런타임 name | id | role | 원본에 없는 것 |
|---|---:|---:|---:|---|
| 직방 | 43 | 54 | 8 | **0** |
| 다방 | 27 | 22 | 1 | **0** |
| 당근 | 48 | 31 | 4 | **0** |

### 재현본만 갖고 있는 것 — 이것뿐이다

| 속성 | 어디에 | 왜 |
|---|---|---|
| `data-flr` | 직방·다방·당근 | 재현본이 만든 요소 표시 |
| `data-flr-list` · `data-flr-opt` | 당근 | 선택지 목록과 항목 |

**전부 `data-flr` 로 시작한다.** 자동화 코드를 짤 때 이 접두사가 붙은 것은 **실물에 없다.**

### 감사에서 실제로 고친 것

- **직방** — 의뢰 방법 입력칸을 감싸는 `<div>` 에 Tailwind 클래스를 손으로 조합해 붙였는데,
  그 조합이 **원본 두 스냅샷 어디에도 없었다.** 확인해 보니 원본에서는 감싸개 자체가 없고
  입력칸이 행 컨테이너의 직계 자식이며 스타일은 input 자신이 갖고 있었다.
  → 클래스를 떼고 `data-flr` 만 남겼다.

### 알고 넘어가는 차이

원본에 없는 것을 *더하지는* 않았지만, 다음은 실물과 다르다.

| 차이 | 내용 |
|---|---|
| **구조 깊이** | 재현본이 만든 요소는 감싸개 `<div>` 가 한 겹 더 있다. 이름·텍스트로 찾으면 무관하지만 **경로(nth-child) 기반 셀렉터는 다르게 걸린다** |
| **직방 선택지 항목** | 실물의 `[role=option]` 에는 `aria-selected`·`data-state`·`data-radix-collection-item`·`<span id>` 이 있는데 재현본에는 없다. **덜 넣은 것이지 없는 걸 지어낸 것은 아니다** |
| **당근 선택 값 클래스** | 고르면 `seed-input-button__placeholder` → `seed-input-button__value` 로 바뀐다(실물과 동일). 다만 **그 클래스의 CSS 규칙이 스냅샷에 없다** — 쓰인 적이 없어 빌드에 안 들어갔다. 상속으로 렌더되는데 회색→검정으로 바뀌어 결과는 실물과 같다 |
| **당근 선택지 상자** | 항목 버튼의 클래스는 관측값 그대로지만, **감싸는 상자는 이쪽에서 만들었다.** 실물의 목록 컨테이너 마크업은 어디에도 기록되지 않았다 |
| **당근 `trades.N`** | s2 스냅샷의 번호를 그대로 쓴다. 아래 「⚠」 참조 |

### 선택지 텍스트 검증

당근의 선택지는 카탈로그에서 만들어 넣으므로 글자가 틀리면 곧 거짓이 된다.
`clickables` 의 `div:nth-child(N)` 순서로 뽑은 관측값과 **글자·순서까지 전부 대조했다.**

```
salesType            카탈로그 11 · 관측 11 · 완전일치
buildingUsage        카탈로그 29 · 관측 29 · 완전일치
buildingOrientation  카탈로그  8 · 관측  8 · 완전일치
```

## 다방 — 직방과 사정이 아주 다르다

**다방 스냅샷은 절반이 이미 살아 있다.** script 는 똑같이 0개지만, 다방은 네이티브 HTML
컨트롤을 쓰기 때문에 브라우저가 알아서 동작시킨다.

| 껍데기 그대로도 되는 것 | 개수 |
|---|---:|
| `<select>` — 눌러도 알아서 펼쳐진다 | 12 |
| `input[type=radio]` | 22 |
| `input[type=checkbox]` | 46 |
| `input[type=text]` · `textarea` | 17 · 2 |

**죽어 있는 것은 `<button>` 25개뿐이다.** 그래서 다방 `live.js` 는 직방보다 훨씬 작다.

### 공여자가 다르다 — 필드로그 기록에서 떼어 왔다

직방은 SingleFile 이 두 번 저장돼 「입력후」 스냅샷을 공여자로 썼다. **다방은 스냅샷이 하나뿐이다.**
대신 필드로그 기록 안의 DOM 조각을 썼다. 조작 기록에는 조작 시점의 주변 DOM
(`actions[].before/after.targetContext.dom`)과 열려 있던 오버레이가 통째로 들어 있고,
**전부 실제로 관측된 마크업**이다.

| 조각 | 크기 | 출처 |
|---|---:|---|
| 달력 전체 | 5,055자 | `a81` 의 열린 오버레이 |
| 단기임대 개월(24) · 협의 여부(3) select | 1,060자 | `a101` 의 조작 문맥 |
| LH 전세임대 필수 동의 체크박스 | 347자 | `a120` 의 조작 문맥 |

### 스냅샷이 「작업 중」 상태라는 점

다방은 빈 폼 스냅샷이 없다. 저장 시점이 작업 도중이라 이렇게 굳어 있다.

- 대분류 = 주택/빌라 · 소분류 = 기타 · 거래 종류 = 월세
- 미등기건물 체크됨 → **그래서 매매 라디오가 처음부터 잠겨 있다**
- 시설 체크박스 다수 켜짐, 날짜·숫자 몇 칸에 테스트 값

**일부러 그대로 두었다.** 어떤 선택지가 켜져 있는지가 지금 보이는 칸들을 결정하기 때문이다.
값을 지우면 화면이 캡처와 달라진다.

## 당근 — 셋 중 가장 죽어 있었다

세 가지가 겹쳤다.

1. **라벨을 눌러도 눈에 보이는 변화가 없다.** 체크박스·라디오의 `<input>` 은 1×1px 로 숨겨져 있고,
   눈에 보이는 표시는 형제 `<div class="seed-checkmark__root">` 다. 그 표시가 켜지는 조건이
   CSS 규칙 `.seed-checkmark__root[data-checked]{…}` 인데, **`data-checked` 는 React 가 붙인다.**
   스냅샷에서는 라벨을 눌러 숨은 input 이 토글돼도 표시가 그대로다.
2. **체크 아이콘 SVG 가 아예 DOM 에 없다.** 켜질 때 주입되는 구조다.
3. **선택지 목록이 하나도 없다.** 닫힌 상태의 `<button>` 12개 중 선택지는 0개.
   매물 종류 11 · 건축물 용도 29 · 방향 8은 전부 열 때 만들어진다.

### 공여자 — 필드로그의 **상태 스냅샷**

다방은 조작 문맥의 DOM *조각*을 썼지만, 당근은 더 좋은 게 있었다.
필드로그의 `states[]` 는 조각이 아니라 **그 시점 문서 전체**다. 두 장이 정확히 필요한 걸 갖고 있었다.

| 상태 | 무엇을 갖고 있나 |
|---|---|
| `s1` (자동: 시작) | 관리비 **「항목별 상세」 갈래** — `*_fixedCost` 8칸 + 항목별 라디오 23개 |
| `s2` (자동: 정지) | 거래유형 5종 **가격 블록 전부** · 관리비 **「간단」 갈래** · **켜진 체크 아이콘** |

원본 스냅샷에서도 하나 건졌다 — 관리비 항목별 「쓴 만큼」이 기본 선택이라
**라디오 아이콘 7개가 이미 그려진 채로** 저장돼 있었다.

### 재현한 것

| 동작 | 근거 |
|---|---|
| **체크 표시 되살리기** — `data-checked` 미러링 + 아이콘 주입 (체크박스·라디오·스위치) | §3-2·3-3·3-5 |
| **선택지 드롭다운 3개** — 매물 종류 11 · 건축물 용도 29 · 방향 8. 팝업이 아니라 그 칸 안에서 아래로 펼쳐진다 | §3-4, §8 |
| 고른 뒤 표시 값과 `aria-label` 갱신 (`매물 종류 선택` → `매물 종류 변경. 현재: 아파트`) | §3-4 |
| **거래 유형 체크 → 가격 블록** 5종 | §6-2 |
| **「10만원 미만…」 체크 → 관리비 본문 통째 교체** (상세 ↔ 간단) | §6-3 `[a239]` |
| 주소·엑셀·등록 봉인 (누르면 안내) | — |

선택지 버튼의 클래스는 `[a11]` 조작 문맥에서 관측된 것을 그대로 쓴다.
**감싸는 상자만 이쪽에서 만들었다** — 목록 컨테이너는 스냅샷에도 기록에도 없다.
선택지 순서는 §8 카탈로그, 즉 `clickables` 의 `div:nth-child(N)` 로 확정한 실제 화면 순서다.

### ⚠ `trades.N` 번호는 s2 의 것을 그대로 쓴다

가격 블록을 s2 에서 통째로 떼어 왔기 때문에, 월세 블록은 `trades.0.*`, 단기 블록은 `trades.4.*`
이름을 달고 있다. **월세와 단기만 체크해도 0 과 4 로 나온다.**

실물이 이때 어떻게 번호를 매기는지는 **원본 캡처로 확정되지 않았다**(§6-2 「미확정」).
재현본의 번호를 실물의 규칙이라고 읽으면 안 된다.

### 재현하지 않은 것

| 무엇 | 왜 |
|---|---|
| **주소 모달** (검색 → 결과 선택 → 상세주소 3단계) | 기록에는 있지만 검색 결과에 중개사무소의 최근 취급 주소가 섞여 있다. 넣지 않았다 |
| 주차 대수 · 권리금 · 전입신고 · 저/중/고 | 조작 문맥에 마크업이 남지 않았다 (해당 구간이 `mutations` 유실 구간과 겹친다) |
| 매물 종류를 바꿨을 때의 칸 교체 (§6-4) | 위와 같은 이유 |
| 관리비 부과 방식 3갈래 중 「기타 부과」·「확인 불가」 | s1·s2 가 둘 다 「정액 관리비」 상태였다 |
| 날짜 칸 | 당근은 인페이지 달력이 없다. 브라우저 네이티브 picker 라 재현 대상이 아니다 (§3-6) |
| 사진·평면도·동영상 업로드 | 서버가 하는 일 |

### 개인정보 — 재현본이 원본보다 안전하다

원본 스냅샷에는 중개사무소명·안심번호·최근 취급 주소 4건이 그대로 남아 있다.
**재현본은 빌드할 때 이것들을 가린다.**

```
최근 주소 칩 4개 → 「최근 주소 1~4」
사무소명 2곳(텍스트 + img alt) → 「○○공인중개사사무소」
안심번호 → 010-****-****
```

집주인 전화번호 칸의 `010-1234-1234` 는 **폼의 예시 placeholder** 라 그대로 둔다.
빌드 마지막에 실제 번호·주소·사무소명이 남았는지 다시 검사하고, 남아 있으면 빌드를 중단한다.

⇒ **당근 재현본은 팀 밖으로 공유해도 된다.** 원본 스냅샷은 안 된다.
