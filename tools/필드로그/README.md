# 필드로그 (FieldLog)

폼 자동입력에 필요한 **DOM 상태와 실제 조작 흐름**을 한 번의 방문으로 기록하는 현장 조사 도구.
내보내는 JSON 형식은 `schemaVersion: 2`다.

> 자동입력 도구와는 **성격이 다르다.** 자동입력은 칸을 *채우는* 쪽, 필드로그는 칸과 반응을
> *기록하는* 쪽이다. 서로 참조하거나 통신하지 않는다.

## 무엇을 기록하나

| 기록 | 알 수 있는 것 |
|---|---|
| 이름 붙은 상태 | 시작·정지 시점과 `관리비 모달 열림` 같은 중간 시점의 DOM, 필드 상태, 열린 팝업 |
| 필드 구조 | 태그·name·id·라벨·DOM 경로·후보 셀렉터·옵션·현재값·선택/비활성/포커스 상태 |
| 실제 조작 | 클릭·변경 같은 의미 단위 조작과 대상 주변 DOM의 **전/후** 변화 |
| 원시 이벤트 | 포인터·포커스·키보드·`beforeinput`·`input`·`change`·한글 조합 시작/진행/완료 순서 |
| 동적 변화 | 노드 추가/삭제, 속성 변경, 필드 등장·숨김·재표시, 옵션 목록 변화 |
| 특수 UI | 라디오·체크박스·콘텐츠 편집 칸·ARIA 기반 커스텀 컨트롤·달력·드롭다운·모달 |
| 경계 정보 | iframe의 위치 정보와 접근 가능한 **open Shadow DOM** 내부 구조 |

각 상태에는 정리된 HTML, 필드별 실행 중 속성, 최소한의 계산된 스타일, 위치·크기와
클릭 가림 여부가 함께 담긴다. 스크린샷은 필요할 때만 별도 PNG로 남긴다.

기록 한 건은 URL 하나가 아니라 **브라우저 문서·프레임 하나**에 대응한다. 불투명한
`captureId`와 마스크 모드를 저장 키로 쓰므로 같은 URL을 연 탭이 여러 개거나 같은 URL의 iframe이
여러 개여도 서로 덮어쓰지 않는다. 같은 문서에서도 가리기 전후 기록은 별도로 보관된다.

초기 화면에 없던 칸은 조건 선택, AJAX, 모달을 거친 뒤에 나타난다. 그래서 시작 화면의
HTML 한 장이나 스크린샷 한 장만으로는 자동입력을 설계할 수 없다. **어떤 조작 뒤에 어떤
상태가 됐는지**를 이어서 남기는 것이 필드로그의 핵심이다.

## 설치 (압축해제 로드 · 심사 배포 없음)

1. 이 폴더를 대상 PC의 **바탕화면에 복사**한다.
   USB에서 바로 로드하면 USB를 뺀 뒤 확장이 깨지므로 피한다.
2. 주소창에 `chrome://extensions` 입력
3. 우측 상단 **개발자 모드** 켜기
4. **압축해제된 확장 프로그램을 로드** → 이 폴더 선택
5. 툴바 퍼즐 아이콘 → 필드로그를 **고정(핀)**

필드로그는 내부 조사용이며 웹스토어에 올리지 않는다. 정책 때문에 개발자 모드가 막혀 있으면
아래 **예비수단**을 쓴다.

## 현장 절차

필드로그는 **특정 플랫폼에 묶여 있지 않다.** 아무 http/https 사이트에서나 쓴다 — 부동산
등록 폼이든 취업사이트 지원서든 상관없다.

**녹화 시작은 그때 보고 있는 탭에만 적용된다.** 그 탭 안의 모든 프레임(교차출처 iframe 포함)이
대상이며, 열어둔 다른 탭은 건드리지 않는다. 시작한 사이트(origin)와 같은 곳이면 페이지를
옮겨다녀도 이어서 기록되고, **정지**는 그 사이트를 띄운 탭들만 찾아가 최종 저장을 시킨다.

1. 조사할 폼을 열고 되도록 **아무 값도 넣지 않은 상태**로 둔다.
2. 툴바 아이콘을 열어 현장 메모를 적고, 필요하면 **입력값 가리기**를 켠 뒤
   **녹화 시작**을 누른다.
   이미 열려 있던 탭은 콘텐츠 스크립트가 붙도록 새로고침한다. 우측 상단 `● REC`가 뜨면
   기록 중이다. 시작 시점은 자동으로 상태 기록된다.
3. 체크리스트의 동작을 하나씩 수행한다. 클릭·입력·한글 조합·DOM 변화와 조작 전후의
   대상 주변 구조는 자동으로 기록된다.
4. 모달, 달력, 드롭다운, 조건부 섹션처럼 중요한 화면이 완성될 때마다 **그 대상 탭을 활성화한 뒤** 팝업의
   **현재 상태 이름**에 알아보기 쉬운 이름을 적고 **현재 상태 기록**을 누른다.
   예: `주소 검색결과 표시`, `관리비 모달 열림`, `전체층 선택 후`.
   팝업은 활성 탭의 대상 프레임 목록을 조회해 각 프레임에 정확히 요청하고, 프레임별 저장 응답을
   모두 확인한 뒤 완료를 표시한다.
5. 화면 모양도 근거로 필요할 때만 **화면 PNG도 저장**을 체크한다. PNG는 JSON에 들어가지
   않고 다운로드 파일로 따로 저장되며, JSON에는 파일명 등 연결 정보만 담긴다.
6. 페이지를 옮겨도 된다. 새 문서와 각 iframe은 별도 기록이 되고, 같은 문서에서 녹화를 다시
   시작하면 그 문서의 같은 마스크 모드 기록에 이어진다.
7. 끝나면 팝업에서 **정지**를 누른다. 정지 시점도 자동으로 상태 기록되고, **이번에 녹화한
   기록만 담은 JSON 이 다운로드 폴더의 `fieldlog/` 아래로 자동 저장된다.** 파일 이름에는
   메모와 그 사이트의 호스트가 들어간다 — 예: `fieldlog_직방-1차_ceo.zigbang.com_2026-09-08T19-40.json`.

### SingleFile 로 두 번 같이 저장한다

필드로그와 **별개로**, 브라우저 확장 SingleFile 로 페이지 전체를 두 번 저장한다.

1. 폼을 열자마자 한 번 (녹화 시작 직전)
2. 작업이 끝나고 **새로고침한 뒤** 한 번 더

두 스냅샷을 비교하면 `id`·`name` 이 페이지를 새로 열 때마다 바뀌는지 바로 판정된다.
필드로그는 한 세션만 보므로 이 판정을 할 수 없다. 실제로 당근에서 이 방법으로
`field:_r_54_:input` → `field:_r_cu_:input` 처럼 **id 가 100% 바뀌는 것**을 확정했고,
`aria-label` 이 안정적인 대안이라는 것도 정적 HTML 에서 찾았다
(`captures/2026-09-08-현장수집/당근부동산/DOM-전수조사.md` §0·§5-1).

반대로 SingleFile 만으로는 부족하다. 같은 폼에서 정적 저장은 name 34종, 필드로그는 60종을
담았고, **차이 26종이 전부 조작해야 나타나는 칸이며 거기에 가격 칸 12개가 통째로 들어간다.**
둘은 대체재가 아니라 보완재다.

### 사이트를 여러 개 도는 경우

한 사이트씩 **시작 → 조작 → 정지**를 반복하면 된다. 정지할 때마다 그 세션에서 만진 기록만
따로 파일이 되므로, 사이트별로 파일이 하나씩 남는다. 다른 탭을 열어둔 채로 해도 되고,
정지 전에 그 탭을 닫아도 닫히는 순간 저장된 내용까지는 파일에 들어간다.

크롬 저장소에는 기록이 계속 쌓인다. `JSON 저장` 버튼은 **쌓인 전체**를 한 파일로 내보내는
용도이고, 다 끝난 뒤 `기록 지우기`로 비운다. 보낼 것은 `fieldlog/` 폴더를 통째로 압축하면 된다.

### 현장에서 볼 것

- 셀렉트를 선택한 뒤 다른 셀렉트의 옵션이 늘어나는가
- 날짜 칸을 클릭했을 때 어떤 달력 또는 팝업이 열리는가
- 탭·라디오·버튼을 누른 뒤 어떤 조건부 섹션과 칸이 나타나는가
- 모달 안에서 다시 어떤 입력·선택·확인 과정이 이어지는가
- 입력값이 자동서식되거나 다른 칸으로 자동환산되는가
- 한글 입력 시 어떤 조합 이벤트 순서로 값이 완성되는가

자동서식·자동환산은 실제로 값을 넣어야 알 수 있다. 이 경우 테스트용 값만 쓰고,
**등록·저장·제출 버튼은 절대 누르지 않는다.** 실매물 등록이나 실제 지원서 접수가 될 수 있다.

## 개인정보와 화면 PNG

**입력값 가리기**는 사용자가 입력한 값과 입력 이벤트의 문자, 민감한 이름의 칸에 담긴 문자열을
가리는 기능이다. 자동입력 설계에 필요한 정적 라디오/옵션의 값과 문구, `checked` 상태와
`selectedIndex`는 일부러 보존한다. 정적 라벨, 버튼 문구, URL, 페이지 제목과 일반 본문뿐 아니라
현장 메모와 사용자가 붙인 상태 이름도 그대로 남는다. 따라서 완전 익명화 기능이 아니다.
민감한 계정명이나 소유자명이 화면 일반 문구·메모·상태 이름에 있으면 JSON에 남을 수 있다.

화면 PNG에는 입력값 가리기가 적용되지 않는다. 브라우저에 보이는 내용이 그대로 찍힌다.
가리기를 켠 상태에서 PNG를 요청하면 팝업이 별도로 경고하지만, 파일 내용을 대신 검수해주지는
않는다.

- 가능하면 빈 폼과 가짜 테스트 값으로 수집한다.
- JSON과 PNG를 반출하기 전에 직접 열어 개인정보가 없는지 확인한다.
- 전달·보관은 사무실이 동의한 경로로만 한다.
- 팝업의 **기록 지우기**는 내려받은 PNG 파일까지 삭제하지 않는다.

## iframe과 Shadow DOM

네모 등록폼은 `register.nemoapp.kr` 교차출처 iframe이다. 확장에는 `all_frames: true`와
해당 호스트 접근 범위가 설정되어 있어 각 프레임의 `recorder.js`가 자기 DOM을 독립된
`captureId`에 기록한다. 상태에는 프레임 깊이·referrer·부모 출처와 크롬의 `frameId` 같은 연결
정보도 포함된다.

팝업의 **현재 상태 기록**은 첫 응답 하나만 성공으로 간주하지 않는다. `webNavigation`으로 활성
탭의 실제 프레임을 열거한 뒤, 대상 프레임 ID마다 상태 기록을 보내고 각 응답(ACK)을 기다린다.
그래서 `webNavigation` 권한이 필요하며, 방문 기록 수집이나 네트워크 전송을 위한 권한은 아니다.

웹 컴포넌트의 **open Shadow DOM**은 내부까지 탐색하고 상태를 별도로 남긴다. 웹페이지가
의도적으로 닫은 **closed Shadow DOM** 내부는 브라우저 규칙상 읽을 수 없다.

## 예비수단 — 확장 설치가 막힌 PC

`recorder.js`는 콘솔에 그대로 붙여넣어도 동작한다.

1. F12 → Console. 크롬이 요구하면 `allow pasting` 입력
2. 값까지 가리려면 먼저 `__flMask = true` 실행
3. `recorder.js` 전체를 붙여넣기 → 즉시 녹화 시작
4. 중요한 상태마다 `상태("관리비 모달 열림")`처럼 실행
5. 끝나면 `끝()` → 팝업 저장과 같은 `schemaVersion: 2` 봉투 형식의 JSON 다운로드

콘솔 방식의 결과도 최상위 `pages` 배열, `pageCount`, `stateCount`, `screenshots`를 갖는 v2
형식이다. 다만 페이지를 이동하면 끊기므로 **이동 전에 `끝()`**으로 저장하고 새 페이지에서 다시
시작한다. 교차출처 iframe은 DevTools 상단 컨텍스트 선택기에서 해당 프레임을 고른 뒤 실행한다.
콘솔 방식에서는 팝업의 별도 PNG 저장 기능을 쓸 수 없다.

## 결과가 해주는 것과 못 해주는 것

필드로그 v2 결과로 각 플랫폼에서 **무엇을 찾아 어떤 이벤트 순서로 조작해야 하는지**, 그리고
그 결과 어떤 모달·옵션·조건부 필드가 생기는지를 조사할 수 있다. 셀렉터 하나와 화면 한 장에
의존하는 것보다 자동입력 어댑터를 만들 근거가 훨씬 많아진다.

하지만 상태 기록은 웹앱 전체를 복제하는 파일이 아니다. 플랫폼 JavaScript의 내부 메모리,
서버 응답, 로그인 세션, 네트워크 타이밍까지 재생하지는 못한다. 기록으로 어댑터를 만든 뒤에도
실제 사이트에서 **등록 버튼을 누르지 않는 드라이런**으로 검증해야 한다.

한 문서·프레임 레코드에는 원시 이벤트 최대 4,000개, DOM 변이 2,500개, 상태 120개를 담는다.
상태의 정리된 DOM은 최대 500,000자, 각 open Shadow DOM은 160,000자다.

**상한에 닿았을 때 무엇이 버려지는지는 종류마다 다르다.**

| 기록 | 상한 | 넘치면 |
|---|---:|---|
| `interactionEvents` | 4,000 | `shift()` — **오래된 것**을 버리고 최근 것을 남긴다 (`recorder.js:896`) |
| `mutations` | 2,500 | **새 것**을 버린다. 앞부분만 남는다 (`recorder.js:970`) |
| `states` | 120 | 새 것을 버린다 (`statesDropped` 증가) |

긴 조사에서는 `interactionEventsDropped`, `mutationsDropped`, `statesDropped`와 HTML의
`truncated` 표시를 확인한다. 값이 있으면 필요한 구간을 여러 녹화 세션으로 나눠 다시 수집한다.

## 2026-09-08 현장 수집에서 드러난 문제

첫 실사용(직방·다방·당근 등록폼) 기록을 전수로 다시 읽으면서 확인된 것들이다.
**추측이 아니라 수집된 JSON과 `recorder.js` 에서 직접 확인한 사실만 적는다.**

의 각 「이 문서가 다루지 못하는 것」 절이 같은 내용을 플랫폼별로 다시 언급한다.

### 1. `mutations` 는 앞부분만 남고 후반부가 통째로 없다

`pushMutation` 이 상한에서 **새 항목을 버리기** 때문에, 남은 기록은 항상 세션 앞부분이다.
세 등록폼 모두 상한에 닿았고, 닿은 시각은 페이지가 얼마나 시끄러운지에 따라 달랐다.

| 플랫폼 | 남은 구간 | 초당 변이 | 실제 발생 | 버려짐 | 세션 길이 |
|---|---|---:|---:|---:|---:|
| 당근 | 0.9 → **44.4초** | 90.9 | 25,087 | 22,587 | 276초 |
| 직방 | 0.06 → **74.0초** | 39.2 | 15,257 | 12,757 | 389초 |
| 다방 | 0.6 → **63.0초** | 36.3 | 7,762 | 5,262 | 214초 |

같은 회차의 다른 사이트(삼성커리어스 1,057 · 공실박스 1,537 · 디디하우스 80)는 상한에 닿지
않았다. **등록폼처럼 지도·애니메이션이 도는 페이지에서만 문제가 된다.**

결과적으로 **후반부에 조작한 칸의 DOM 변이 근거가 없다.** 그 구간은 `actions`·`timeline`·
상태 스냅샷으로만 판단해야 한다.

### 2. 상한에 닿아도 계산 비용은 줄지 않는다

버릴지 말지는 `pushMutation` 안에서 판단하는데, 인자로 넘길 객체는 그 전에 이미 다 만든다.
`nodeSummary` 는 노드마다 `pathOf` 로 조상을 최대 24단계 훑어 셀렉터 문자열을 만든다
(childList 하나당 target + 추가 최대 30 + 삭제 최대 30개).

```js
pushMutation({ ..., target: nodeSummary(m.target), added, removed, ... })
//                  ↑ 여기서 다 계산한 뒤
//   pushMutation 안에서 "상한 초과" 판정을 받고 버려진다
```

당근 기준 **44초 이후 남은 230여 초 동안 22,587번**이 이렇게 계산되고 버려졌다.

### 3. 저장할 때마다 기록 전체를 다시 직렬화한다

`queueSave()` 는 변화가 있을 때마다 1.2초 뒤 `saveNow()` 를 부르고,
`saveNow()` 는 `chrome.storage.local.set({ [PAGE_KEY]: finalized, ... })` 로
**레코드 전체**를 쓴다. 부분 갱신이 아니다. 레코드는 세션 내내 커지기만 하므로
저장 1회의 비용이 단조 증가한다. 세션 종료 시점 크기:

| 플랫폼 | 레코드 전체 | 원시 이벤트 | 조작 | 변이 | 상태 | 칸 | 클릭대상 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 당근 | **13.5MB** | 7.5MB | 2.9MB | 1.5MB | 0.8MB | 0.5MB | 0.3MB |
| 직방 | **12.6MB** | 3.6MB | 4.7MB | 1.3MB | 0.9MB | 0.9MB | 1.0MB |
| 다방 | **13.7MB** | 5.9MB | 5.2MB | 1.4MB | 0.4MB | 0.4MB | 0.3MB |

`unlimitedStorage` 권한이 있어 **용량 초과로 저장이 실패하지는 않았다**
(모든 파일이 온전하게 내보내졌다). 비용은 실패가 아니라 반복 직렬화 쪽이다.

### 4. 용량의 대부분은 경로 문자열이다

| 플랫폼 | 이벤트 | 건당 | 그중 `composedPath` |
|---|---:|---:|---:|
| 당근 | 1,326건 / 7.5MB | 5.8KB | **6.4MB (85%)** |
| 직방 | 1,036건 / 3.6MB | 3.5KB | **2.9MB (81%)** |
| 다방 | 1,311건 / 5.9MB | 4.6KB | **4.7MB (80%)** |

원시 이벤트마다 조상 14개의 CSS 경로를 문자열로 담는데, 당근·다방은 경로 한 줄이 300자를
넘는다. `actions` 도 마찬가지로 `before`/`after` 의 주변 DOM 문자열이
**당근 41% · 직방 76% · 다방 45%** 를 차지한다.

### 5. 스윕이 굶어서 `afterAction` 이 실제 원인과 어긋난다

DOM 변이가 오면 300ms 뒤에 `sweep()` 이 예약되는데, 새 변이가 오면 `clearTimeout` 으로
다시 밀린다. 애니메이션이 쉬지 않는 페이지에서는 스윕이 계속 뒤로 밀린다.
기록된 구간에서 **300ms 넘는 틈은 당근 45회 · 직방 26회 · 다방 30회**뿐이었다.

그래서 `timeline[].afterAction` 은 **원인 조작이 아니라 스윕 직전의 마지막 조작**을 가리킨다.
실측 예:

- 다방 `buildingTradeUnitType` 재등장이 `a52`(주소 검색 클릭)로 기록됐으나,
  `mutations` 의 실제 시각은 그보다 앞선 `a47`(다가구주택 선택) 직후였다.
- 다방 「건물 전체」 선택의 여파 전체가 `a52` 로 몰려 기록됐다. 실제 변이는 45.42초,
  즉 `a49/a50` 직후다.

⇒ **인과를 확정하려면 `mutations` 의 시각을 봐야 한다. `afterAction` 만 믿으면 안 된다.**

### 6. `fields[].transitions` 가 재등장을 놓치는 경우가 있다

당근 「전입신고 불가능 / 해당」 체크박스는 `added`(25.8초) · `removed`(32.8초) 두 건만
기록됐다. 그런데 같은 레코드의 `lastSeen` 은 세션 끝(275.7초)이고, 정지 시점 상태 DOM에도
그 칸이 실제로 존재한다. **`readded` 전이가 남지 않았다.**

⇒ 칸의 존재 여부는 `transitions` 보다 **상태 DOM과 `lastSeen`/`lastRemoved`** 가 정확하다.

### 7. `sideEffects` 가 인접한 다른 클릭을 잘못 물고 온다

값 변경 뒤 250~450ms 안에 다른 칸이 바뀌면 부수효과로 기록되는데, 그 사이에 사용자가
**관계없는 컨트롤을 클릭**하면 그것까지 딸려 들어간다. 확인된 오귀속 3건:

| 파일 | 기록된 내용 | 실제 |
|---|---|---|
| 직방 | `ho` 입력 → 「단일동」 체크박스가 `false→true` | `ho` 변경 26.4초, 단일동 클릭 26.5~26.6초. 별개 조작 |
| 직방 | `sales.rent` 입력 → `jibun-open` 이 `''→'on'` | `rent` 변경 47.01초, 「단독주택」 클릭 47.16초. `jibun-open` 은 그 선택으로 다시 마운트된 것 |
| 다방 | 「방 수」 입력 → 「오픈형」 라디오가 `false→true` | 별개 조작 |

당근에서 확인된 부수효과(㎡↔평 양방향 환산, 숨은 date 칸 → 보이는 날짜 칸)는 전부 사실이었다.
**부수효과는 항상 조작 시각과 대조해야 한다.**

### 8. `actions[].after` 는 250~450ms 뒤 값이라 연속 클릭에 뒤집힌다

`after` 는 클릭 450ms · 값변경 250ms 뒤에 읽는다. 그 사이 다음 조작이 들어가면
이미 다음 상태가 찍힌다. 다방 `[a190]` 은 「개별난방」 선택인데 `after.checked` 가 `false` 다 —
그 사이에 「중앙난방」을 눌렀기 때문이다. `before` 도 pointerdown 시점 캐시를 3초까지
재사용하므로 빠른 연속 클릭에서는 직전 상태가 아닐 수 있다.

⇒ **`before`/`after` 쌍으로 상태 변화를 읽지 말고, `change` 액션의 순서로 읽어야 한다.**

### 9. 그 밖에 관측된 것

- **`판정` 의 날짜 오탐.** 당근 `lessorPhoneNumber`(placeholder `010-1234-1234`)가
  「날짜」로 분류됐다. `verdict()` 의 날짜 힌트 정규식이 `\d{4}[-.]?\d{2}` 에 걸린 결과다.
- **`options` 가 0이라고 선택지가 없는 것은 아니다.** 당근은 `<select>` 를 하나도 쓰지 않아
  전부 0이었다. 선택지는 `clickables` 에 있었다.
- **한 레코드에 두 세션이 합쳐진다.** 직방 `pages[0]` 은 `sessions: 2` 로, 매물 *목록* 화면과
  등록폼이 한 레코드에 섞여 있다. `fields` 347개를 폼 칸 수로 읽으면 틀린다
  (등록폼 안은 75개). 구분하려면 `states[]` 의 `url` 을 봐야 한다.


## 구성

```text
필드로그/
├── manifest.json       대상 사이트·권한
├── recorder.js         schema v2 녹화 엔진 (확장·콘솔 겸용, 현장 수집의 기준)
├── popup.html/.js      시작·정지·상태 기록·JSON/선택적 PNG 저장 UI
├── icon*.png
└── dev/                자체점검 (현장에서는 불필요)
    ├── _selftest.html  녹화 엔진 점검
    └── _popuptest.html 팝업 UI 점검
```

권한은 `storage`(문서·프레임 기록 누적), `unlimitedStorage`, `downloads`, `activeTab`,
`webNavigation`이다. `activeTab`은 사용자가 체크한 현재 화면 PNG를 명시적으로 찍을 때,
`webNavigation`은 현재 상태 기록 시 활성 탭의 프레임을 열거하고 각 응답을 확인할 때만 쓴다.
콘텐츠 스크립트는 모든 http/https 페이지에 주입되지만, **주입과 기록은 다르다.** 기록은
사용자가 그 탭에서 **녹화 시작**을 눌렀을 때만 시작하고, 자동 재개도 그때 저장한 origin
목록에 있는 페이지에서만 일어난다. 열어둔 다른 탭은 기록되지 않는다. 네트워크 전송 코드는
없으며, DOM 기록은 그 PC의 크롬 저장소에 머물다가 JSON으로 다운로드된다.

## 자체점검

`chrome.storage`와 팝업 API를 흉내낸 점검 페이지에서 실제 확장 코드를 실행한다.

```bash
python3 -m http.server 8778 --bind 127.0.0.1 --directory ~/Documents/한방/tools/필드로그
```

- `http://127.0.0.1:8778/dev/_selftest.html` — 필드·커스텀 컨트롤·이벤트·상태·Shadow DOM·
  동적 변화·문서/프레임 분리·저장 경쟁 조건 등 녹화 엔진
- `http://127.0.0.1:8778/dev/_popuptest.html` — 시작/정지·프레임별 상태 응답·선택적 PNG·
  v2 내보내기·기록 지우기 등 팝업

숨겨진 탭에서는 `setTimeout`이 약 1초로 제한될 수 있다. 그래서 점검은 고정 대기가 아니라
조건 폴링으로 짜여 있다. 새 검사를 추가할 때도 같은 방식을 유지한다.
